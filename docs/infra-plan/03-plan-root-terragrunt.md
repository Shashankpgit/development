# Plan 03 — Root Terragrunt Config

## What we are building in this step

One file: `infra/live/terragrunt.hcl`

This is the most important Terragrunt file. Every module under `infra/live/vault/`
inherits from it. It does three things:
1. Configures where OpenTofu stores its state (the GCS bucket from Plan 02)
2. Injects the `google` provider into every module automatically
3. Passes `project_id` and `region` to every module as shared inputs

---

## File: `infra/live/terragrunt.hcl`

### Block 1: locals

```hcl
locals {
  project_id = get_env("GCP_PROJECT_ID")
  region     = get_env("GCP_REGION")
  bucket     = get_env("TF_STATE_BUCKET", "vault-tofu-state")
}
```

`locals` — a block for values you want to compute once and reuse inside this file.
These are not passed to child modules directly; they are used within this file's
other blocks.

`get_env("VAR_NAME")` — Terragrunt reads the environment variable `VAR_NAME` from
the current shell. This is how the values from `infra/infra.env` (which the shell
script `source`d) reach Terragrunt.

`get_env("VAR", "default")` — if the env var is not set, use the default. We use
this for `TF_STATE_BUCKET` so that running `terragrunt` manually (without sourcing
`infra.env`) doesn't fail immediately.

Why env vars instead of hardcoding?
- `infra.env` is gitignored (real project ID stays off git)
- The same root `terragrunt.hcl` works for any project — just change `infra.env`
- CI/CD can set these as GitHub Secrets instead of a file

### Block 2: remote_state

```hcl
remote_state {
  backend = "gcs"
  generate = {
    path      = "backend.tf"
    if_exists = "overwrite_terragrunt"
  }
  config = {
    bucket = local.bucket
    prefix = path_relative_to_include()
  }
}
```

`remote_state` — tells Terragrunt where OpenTofu should store its state file.

`backend = "gcs"` — use Google Cloud Storage as the backend. OpenTofu supports
other backends (S3, Azure Blob, Terraform Cloud), but GCS is the native choice for GCP.

`generate { path = "backend.tf" ... }` — instead of adding a `terraform { backend
"gcs" {} }` block to every module, Terragrunt generates a `backend.tf` file in each
module's working directory automatically before running `tofu`. This is the DRY
(Don't Repeat Yourself) benefit of Terragrunt.

`if_exists = "overwrite_terragrunt"` — if a `backend.tf` already exists (from a
previous Terragrunt run), overwrite it. The `_terragrunt` suffix means "only overwrite
if Terragrunt generated it, not if a human wrote it."

`prefix = path_relative_to_include()` — the most important line in this block.
`path_relative_to_include()` is a Terragrunt built-in function that returns the path
of the calling module relative to this root file.

Example:
```
This file is at:     infra/live/terragrunt.hcl
apis module is at:   infra/live/vault/apis/terragrunt.hcl
Relative path:       vault/apis

Network module at:   infra/live/vault/network/terragrunt.hcl
Relative path:       vault/network
```

So each module gets a unique GCS key:
```
gs://vault-tofu-state/vault/apis/terraform.tfstate
gs://vault-tofu-state/vault/network/terraform.tfstate
gs://vault-tofu-state/vault/gke/terraform.tfstate
```

No two modules write to the same file. This is what prevents state corruption.

### Block 3: generate "provider"

```hcl
generate "provider" {
  path      = "provider.tf"
  if_exists = "overwrite_terragrunt"
  contents  = <<-EOF
    terraform {
      required_providers {
        google = {
          source  = "hashicorp/google"
          version = "~> 5.0"
        }
      }
      required_version = ">= 1.6"
    }

    provider "google" {
      project = "${local.project_id}"
      region  = "${local.region}"
    }
  EOF
}
```

`generate "provider"` — Terragrunt generates a `provider.tf` file in each module's
working directory before running `tofu`. Without this, every module would need to
declare the provider itself.

`contents = <<-EOF ... EOF` — a heredoc. Everything between `EOF` markers becomes
the file content. Terragrunt evaluates `${local.project_id}` and
`${local.region}` before writing the file, so the generated `provider.tf` contains
the actual project ID and region as strings.

**What gets generated in each module's working directory:**
```hcl
# This file is generated by Terragrunt — do not edit
terraform {
  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 5.0"
    }
  }
  required_version = ">= 1.6"
}

provider "google" {
  project = "vault-project-123456"
  region  = "asia-south1"
}
```

`version = "~> 5.0"` — the `~>` operator means "5.0 or any later 5.x version, but
not 6.0". This is called a pessimistic version constraint. It allows patch and minor
updates within v5, but protects against breaking changes in v6.

`required_version = ">= 1.6"` — the minimum OpenTofu (or Terraform) version. Ensures
everyone on the team uses a compatible version.

### Block 4: inputs

```hcl
inputs = {
  project_id = local.project_id
  region     = local.region
}
```

`inputs` — values passed to every module as OpenTofu variables. Every module that
declares `variable "project_id"` and `variable "region"` receives these automatically
without having to redeclare them in each module's `terragrunt.hcl`.

This is the third DRY benefit of Terragrunt: shared inputs set once, inherited everywhere.

## How a child module uses this root config

Each child module's `terragrunt.hcl` includes this root file:

```hcl
# infra/live/vault/apis/terragrunt.hcl

include "root" {
  path = find_in_parent_folders()
}
```

`find_in_parent_folders()` — walks up the directory tree from the current file until
it finds a `terragrunt.hcl`. The first one it finds (in `infra/live/`) is our root
config. The child module inherits all three blocks: `remote_state`, `generate`, and
`inputs`.

---

## The complete picture for one module

When you run `terragrunt apply` inside `infra/live/vault/network/`:

```
Terragrunt reads:
  infra/live/vault/network/terragrunt.hcl     ← the module's own config
  infra/live/terragrunt.hcl                   ← root config (via include)

Terragrunt generates (in .terragrunt-cache/):
  backend.tf    ← from remote_state block
  provider.tf   ← from generate "provider" block

Terragrunt runs:
  tofu init     ← downloads google provider, connects to GCS backend
  tofu apply    ← creates the network resources
```

## Verification for this step

After creating this file (but before creating any modules):

```bash
# source the config
source infra/infra.env

# navigate to any module directory
cd infra/live/vault/apis

# run terragrunt plan — it should:
# 1. Connect to the GCS backend successfully
# 2. Generate provider.tf in .terragrunt-cache/
# 3. Fail because the module source doesn't exist yet (expected at this stage)
terragrunt plan
```

Expected output at this stage:
```
ERRO[0000] Error processing module at 'infra/live/vault/apis/terragrunt.hcl'.
  ...
  source ... does not exist
```

This error is expected — we haven't created the modules yet. But if you see
a GCS connection error, the bucket or credentials are wrong. Fix those first.
