## What Is systemd?

`systemd` is PID 1 — the first process the kernel starts after boot. It initializes the rest of the system: mounts filesystems, brings up the network, starts all services (nginx, MySQL, SSH, etc.).

Before systemd, Linux used `SysVinit` (shell scripts in `/etc/init.d/`). systemd replaced it around 2012-2015 and is now standard on all major distros.

```
Kernel boots
  ↓
Kernel starts /sbin/init (which is systemd on modern systems) as PID 1
  ↓
systemd reads /etc/systemd/system/ and /lib/systemd/system/
  ↓
systemd starts all services defined there, in dependency order
  ↓
System is ready: login prompt, network up, services running
```

## Units — What systemd Manages

Everything in systemd is a **unit**. Different unit types:

```
.service  → A daemon or program (nginx.service, mysql.service)
.timer    → A scheduled task (cron replacement)
.socket   → A socket that activates a service on connection
.target   → A group of units (like runlevels: multi-user.target, graphical.target)
.mount    → A filesystem mount
.path     → Watch a path for changes, activate a service
.device   → A device (usually auto-generated by udev)
```

## systemctl — Controlling Services

```bash
# Check status:
systemctl status nginx
# Output:
# ● nginx.service - A high performance web server and a reverse proxy server
#      Loaded: loaded (/lib/systemd/system/nginx.service; enabled; vendor preset: enabled)
#      Active: active (running) since Sun 2026-07-06 08:00:00 UTC; 2h 15min ago
#     Main PID: 1234 (nginx)
#      Tasks: 3 (limit: 4915)
#     Memory: 24.0M
#        CPU: 350ms
#     CGroup: /system.slice/nginx.service
#             ├─1234 nginx: master process /usr/sbin/nginx
#             ├─1235 nginx: worker process
#             └─1236 nginx: worker process
# Jul 06 08:00:00 systemd[1]: Started A high performance web server

# Start / Stop / Restart:
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx      # stop then start
sudo systemctl reload nginx       # reload config without restart (if supported)
sudo systemctl reload-or-restart nginx  # reload if supported, else restart

# Enable / Disable (start at boot):
sudo systemctl enable nginx       # start on boot
sudo systemctl disable nginx      # don't start on boot
sudo systemctl enable --now nginx # enable AND start immediately

# Mask / Unmask (prevent start even manually):
sudo systemctl mask nginx         # cannot be started at all
sudo systemctl unmask nginx

# List all units:
systemctl list-units --type=service          # all services
systemctl list-units --type=service --state=failed  # only failed services
systemctl list-unit-files | grep enabled    # all enabled units

# What failed:
systemctl --failed
```

## Writing Your Own Service Unit

This is what you'll do when you deploy your application to a server.

### Basic Service Unit

```bash
# Create the file:
sudo nano /etc/systemd/system/myapp.service
```

```ini
[Unit]
Description=My Node.js Application
After=network.target              # start after network is up
After=postgresql.service          # start after postgres
Requires=postgresql.service       # if postgres fails, stop this too

[Service]
Type=simple                       # process stays in foreground
User=myapp                        # run as this user (not root!)
Group=myapp
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/node /opt/myapp/server.js
Restart=on-failure                # restart if it crashes
RestartSec=5                      # wait 5 seconds before restart
Environment=NODE_ENV=production
Environment=PORT=3000
EnvironmentFile=/opt/myapp/.env   # load secrets from file

# Security hardening:
NoNewPrivileges=true              # no privilege escalation
PrivateTmp=true                   # isolated /tmp

[Install]
WantedBy=multi-user.target        # enable in this target (normal boot)
```

```bash
# After creating/editing the file, reload systemd:
sudo systemctl daemon-reload

# Enable and start:
sudo systemctl enable --now myapp

# Check it works:
systemctl status myapp
```

### Service Types

```
Type=simple    (default)
  ExecStart is the main process.
  systemd considers the service started when ExecStart runs.
  The process must stay in the foreground.
  Best for: most modern apps

Type=forking
  ExecStart forks and the parent exits.
  Old-style daemons (nginx, Apache) use this.
  systemd waits for the parent to exit, then considers it started.

Type=oneshot
  Run a command, wait for it to finish, then stop.
  The service is "active" only while the command runs.
  Best for: startup scripts, one-time tasks

Type=notify
  Like simple, but the process sends a notification to systemd
  when it's actually ready (not just started).
  Best for: services that do lengthy initialization (DB connections, cache warmup)
```

### Restart Policies

```
Restart=no          → never restart (default)
Restart=always      → restart no matter what (exit code, signal, timeout)
Restart=on-failure  → restart only on non-zero exit or killed by signal
Restart=on-abnormal → restart on signal, timeout, watchdog failure
```

### Environment Variables from a File

```bash
# Create an env file (keep this out of git — contains secrets):
sudo nano /opt/myapp/.env

# Contents:
DATABASE_URL=postgresql://user:pass@localhost:5432/mydb
JWT_SECRET=very-secret-key
AWS_REGION=ap-south-1

# Permissions: only the service user should read it:
sudo chown myapp:myapp /opt/myapp/.env
sudo chmod 600 /opt/myapp/.env

# Reference in service file:
# EnvironmentFile=/opt/myapp/.env
```

## Targets — Boot States

Targets are like runlevels — they define what set of services should be running.

```
poweroff.target   → Shut down
rescue.target     → Single-user mode (recovery)
multi-user.target → Normal server (no GUI)
graphical.target  → GUI desktop
reboot.target     → Reboot
```

```bash
# Current target:
systemctl get-default
# multi-user.target  (normal for servers)

# Change default:
sudo systemctl set-default graphical.target  # add GUI (don't do this on EC2)

# Switch targets right now (like changing runlevels):
sudo systemctl isolate rescue.target    # go to single-user mode (recovery)
sudo systemctl isolate multi-user.target # back to normal
```

## Journald and journalctl — Reading Logs

All service output (stdout and stderr) goes to the systemd journal. This is centralized, structured, and persistent.

```bash
# View all recent logs:
journalctl

# Follow live (like tail -f):
journalctl -f

# Logs for a specific service:
journalctl -u nginx
journalctl -u nginx -f            # follow nginx logs live
journalctl -u nginx --since "1 hour ago"
journalctl -u nginx --since "2026-07-06 08:00" --until "2026-07-06 09:00"

# Last N lines:
journalctl -u nginx -n 100

# Only errors:
journalctl -u nginx -p err        # err, warning, info, debug
journalctl -p err                  # system-wide errors

# Kernel messages (like dmesg):
journalctl -k
journalctl -k --since "5 minutes ago"   # recent kernel messages

# Since last boot:
journalctl -b                     # current boot
journalctl -b -1                  # previous boot (useful after crash)
journalctl --list-boots           # list all boots with timestamps

# Filter by time:
journalctl --since "yesterday"
journalctl --since "2026-07-01" --until "2026-07-06"

# Output as JSON (for log processing):
journalctl -u nginx -o json | head -5
```

### Journal Storage

```bash
# How much disk space the journal is using:
journalctl --disk-usage
# Archived and active journals take up 256.0M in the filesystem.

# Limit journal size (edit /etc/systemd/journald.conf):
sudo nano /etc/systemd/journald.conf
# [Journal]
# SystemMaxUse=1G      # max disk space for journal
# MaxRetentionSec=30day # keep logs for max 30 days

# Clean old journal entries manually:
sudo journalctl --vacuum-size=500M   # keep only 500MB of logs
sudo journalctl --vacuum-time=7d     # keep only last 7 days
```

## Timers — cron Replacement

systemd timers are a cron replacement with better logging, dependencies, and catch-up behavior.

### Example: Run a Backup Every Night at 2am

```bash
# Create the service that does the actual work:
sudo nano /etc/systemd/system/backup.service
```

```ini
[Unit]
Description=Nightly database backup

[Service]
Type=oneshot
User=backup
ExecStart=/opt/scripts/backup.sh
```

```bash
# Create the timer that schedules it:
sudo nano /etc/systemd/system/backup.timer
```

```ini
[Unit]
Description=Run backup every night at 2am

[Timer]
OnCalendar=*-*-* 02:00:00      # every day at 02:00 UTC
Persistent=true                # run even if machine was off at 2am (catch-up)

[Install]
WantedBy=timers.target
```

```bash
# Enable and start the timer (not the service — the timer starts the service):
sudo systemctl daemon-reload
sudo systemctl enable --now backup.timer

# See all timers and when they'll next fire:
systemctl list-timers

# Output:
# NEXT                        LEFT     LAST                        PASSED  UNIT
# Sun 2026-07-07 02:00:00 UTC 17h left Sat 2026-07-06 02:00:30 UTC 7h ago  backup.timer

# Check timer logs:
journalctl -u backup.service
```

### Timer Schedule Formats

```
OnCalendar=*-*-* 02:00:00      # every day at 2am
OnCalendar=Mon *-*-* 03:00:00  # every Monday at 3am
OnCalendar=*-*-1 00:00:00      # first of every month
OnCalendar=hourly               # every hour
OnCalendar=daily                # every day at midnight
OnCalendar=weekly               # every Monday midnight

OnBootSec=5min                  # 5 minutes after boot
OnUnitActiveSec=1h              # 1 hour after last activation (recurring)
```

## Dependency Management

systemd starts services in the right order based on dependencies declared in unit files.

```
Directive         Meaning
─────────────────────────────────────────────────────────
After=X           Start this unit AFTER X is started (ordering only)
Before=X          Start this unit BEFORE X (ordering only)
Requires=X        X must be running; if X stops, stop this too
Wants=X           Start X too, but don't fail if X fails (weaker Requires)
BindsTo=X         Like Requires, but if X stops for ANY reason, stop this too
```

```bash
# What depends on nginx?
systemctl list-dependencies nginx --reverse

# What does nginx depend on?
systemctl list-dependencies nginx
```

## Practical: Deploy a Python App as a systemd Service

```bash
# Create a dedicated user:
sudo useradd --system --no-create-home --shell /usr/sbin/nologin appuser

# Create the app directory:
sudo mkdir /opt/myapi
sudo chown appuser:appuser /opt/myapi

# Copy your app code to /opt/myapi/
# ...

# Create a virtual environment and install dependencies:
sudo -u appuser python3 -m venv /opt/myapi/venv
sudo -u appuser /opt/myapi/venv/bin/pip install -r /opt/myapi/requirements.txt

# Create the service file:
sudo nano /etc/systemd/system/myapi.service
```

```ini
[Unit]
Description=My Python API
After=network.target

[Service]
Type=simple
User=appuser
Group=appuser
WorkingDirectory=/opt/myapi
ExecStart=/opt/myapi/venv/bin/uvicorn main:app --host 0.0.0.0 --port 8000
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal
SyslogIdentifier=myapi
EnvironmentFile=/opt/myapi/.env
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now myapi
systemctl status myapi
journalctl -u myapi -f
```
